เริ่มจากแยก 2 คำนี้ให้ชัด: Git คือเครื่องมือบนเครื่องของเรา ส่วน GitHub คือบริการบนอินเทอร์เน็ตที่ช่วยเก็บ repo และทำงานร่วมกับคนอื่น

git commit

SETUP ONCE

ติดตั้งครั้งเดียว
ตั้งค่าให้พร้อมใช้งาน

เช็กว่าติดตั้งแล้วหรือยัง

ตรวจสอบค่าที่ตั้งไว้

$ git config --global --list

SAFE EXPERIMENTS

Branch & merge
แยกงานโดยไม่รบกวน main

Branch คือเส้นทางประวัติแยกออกมา ให้เราทดลองฟีเจอร์หรือแก้บั๊กโดยไม่ทำให้ branch หลักเสียหาย

01

สร้างและสลับ branch

คำสั่งสมัยใหม่ที่ทำทั้งสองอย่างในครั้งเดียว

$ git switch -c feature/login
02

ทำงานและ commit

แก้โค้ด ทดสอบ แล้วบันทึกเป็นก้อนเล็ก ๆ

$ git add .
$ git commit -m "add login form"
03

กลับ main

ก่อน merge ให้ดึงประวัติล่าสุดของ main มาก่อนเสมอ

$ git switch main
$ git pull
04

รวม branch

นำฟีเจอร์ที่เสร็จแล้วมารวมใน main

$ git merge feature/login

REMOTE & COLLABORATION

ทำงานกับ remote
ให้ทีมเห็นโค้ดชุดเดียวกัน

Remote คือ repository ที่อยู่บนเซิร์ฟเวอร์ เช่น GitHub, GitLab หรือ Bitbucket คำสั่งหลักมี 3 กลุ่ม: ส่งขึ้น, ดึงลง และดูความเปลี่ยนแปลง

⌂เครื่องเราlocal repo
git push→git pull
◉GitHubremote repo
git remote add origin URL

เชื่อม repo ในเครื่องกับ GitHub ครั้งแรก

git push -u origin main

ส่ง branch main ขึ้น remote และจำคู่ branch ไว้

git fetch origin

ดึงข้อมูลใหม่มาดู แต่ยังไม่รวมเข้าการทำงาน

git pull origin main

ดึงข้อมูลใหม่และรวมเข้ากับ branch ปัจจุบัน

Pull Request แบบสั้นที่สุด

  1. 01
    สร้าง branch

    อย่าทำฟีเจอร์บน main โดยตรง

  2. 02
    push branch ขึ้น GitHub

    git push -u origin feature/login

  3. 03
    เปิด Pull Request

    อธิบายสิ่งที่เปลี่ยน วิธีทดสอบ และแนบ screenshot ถ้ามี

  4. 04
    review → แก้ → merge

    เมื่อผ่านแล้วค่อยรวมเข้า main

07

RECOVERY KIT

แก้พลาดอย่างปลอดภัย
เลือกเครื่องมือให้ตรงอาการ

ก่อนใช้คำสั่งย้อนกลับ ให้ถามตัวเอง 2 ข้อ: commit นี้ถูก push ไปแล้วหรือยัง? และ อยากเก็บการแก้ไขไว้ไหม?

สถานการณ์ใช้คำสั่งผลลัพธ์
แก้ไฟล์แล้วอยากทิ้งการแก้
git restore file.js

คืนไฟล์กลับไปตาม commit ล่าสุด

เผลอ add ไฟล์เข้า staging
git restore --staged file.js

เอาออกจาก staging แต่ไม่ลบการแก้ในไฟล์

อยากแก้ message ของ commit ล่าสุด
git commit --amend

แก้ commit ล่าสุด — ใช้ก่อน push เท่านั้น

commit ไปแล้ว แต่ต้องการแก้แบบปลอดภัย
git revert <commit>

สร้าง commit ใหม่เพื่อหักล้างของเดิม

ต้องย้อน local commit หลายอัน
git reset --soft HEAD~1

ย้ายหัว commit แต่เก็บไฟล์และ staging ไว้

⚠

ระวัง git reset --hard
คำสั่งนี้ทิ้งการเปลี่ยนแปลงที่ยังไม่ commit และกู้คืนยากมาก ใช้เฉพาะเมื่อแน่ใจว่าข้อมูลนั้นไม่ต้องการแล้ว

แก้ merge conflict เป็นขั้นตอน

ONE REPO, MANY AGENTS

หลาย Agent ใน 1 repo
ทำงานพร้อมกันโดยไม่เหยียบกัน

หัวใจสำคัญคือ อย่าให้หลาย Agent ใช้ working tree และ staging area ชุดเดียวกัน ให้แต่ละ Agent มี directory, branch และขอบเขตไฟล์ของตัวเอง แล้วค่อยรวมงานผ่าน Agent กลางหรือ Pull Request

×

รูปแบบที่ควรหลีกเลี่ยง
เปิด Agent A, B และ C ในโฟลเดอร์เดียวกัน เพราะทุกตัวจะแก้ไฟล์และ Git index ชุดเดียวกัน อาจเกิดไฟล์หาย, stage งานของกันและกัน หรือ commit งานผิดชุดได้

01

แยกพื้นที่

หนึ่ง Agent เท่ากับหนึ่ง git worktree และหนึ่ง branch ห้ามแชร์ directory ทำงาน

02

แยก ownership

กำหนดว่า Agent ใดเป็นเจ้าของไฟล์หรือ module ไหน และระบุ shared hotspot ไว้ก่อนเริ่ม

03

รวมงานทีละชุด

ให้ Integrator review, test และ merge ตามลำดับ แล้วแจ้ง Agent ที่เหลือให้อัปเดตฐานใหม่

1. สร้าง worktree แยกให้แต่ละ Agent

รันจาก repository หลัก ตัวอย่างนี้สร้าง directory เป็นพี่น้องกับ repo เดิม แต่ทุก worktree ยังใช้ประวัติ Git ชุดเดียวกัน จึงประหยัดกว่าการ clone ซ้ำ

เตรียมพื้นที่สำหรับ Agent 3 ตัว
$ git fetch origin
$ git worktree add ../repo-agent-auth -b agent/auth origin/main
$ git worktree add ../repo-agent-ui -b agent/ui origin/main
$ git worktree add ../repo-agent-tests -b agent/tests origin/main
$ git worktree list
i

ข้อจำกัดของ worktree
branch เดียวกันไม่สามารถ checkout อยู่ในหลาย worktree พร้อมกันได้ นี่เป็น guardrail ที่ช่วยบังคับให้แต่ละ Agent ใช้ branch แยกกัน

4. Sync และรวมงานอย่างปลอดภัย

01

Worker sync เฉพาะ branch ตัวเอง

ก่อน handoff ให้อัปเดตฐานและรันทดสอบอีกครั้ง

git fetch origin
git rebase origin/main
02

Integrator ดู diff และ test

ตรวจทุก commit เทียบกับ main โดยไม่พึ่งคำอธิบายอย่างเดียว

git diff origin/main...agent/auth
03

Merge ทีละ Agent

หลัง merge แต่ละชุด ให้รัน test ก่อนรับชุดถัดไป

git merge --no-ff agent/auth
04

แจ้ง Agent ที่เหลือ rebase

ลด conflict สะสมโดยให้ทุก branch ขยับตาม main ล่าสุด

git rebase origin/main
!

ใช้ --force-with-lease เฉพาะ branch ของตัวเอง
หลัง rebase อาจต้อง force push แต่ห้าม force push main, integration branch หรือ branch ที่มี Agent อื่นใช้อยู่

ISSUE-DRIVEN DELIVERY

Git style Jira
ให้ ticket เดินไปกับ code

ใช้ Jira key เป็นด้ายเส้นเดียวที่เชื่อม requirement, branch, commit, Pull Request และ deployment เข้าด้วยกัน ตัวอย่างทั้งบทนี้ใช้ ticket PAY-142: “เพิ่มการชำระเงินด้วยบัตร”

i

ต้องเชื่อม development tool ก่อน
Jira จะแสดง branch, commit และ Pull Request ใน Development panel เมื่อผู้ดูแลเชื่อม GitHub, Bitbucket, GitLab หรือเครื่องมือที่รองรับ และทีมใช้ work item key ในกิจกรรม Git

1. Convention กลางของทีม

TICKETPAY-142

Key ต้องเป็นตัวพิมพ์ใหญ่และตรงกับ Jira

BRANCHfeature/PAY-142-card-payment

ประเภท / key / คำอธิบายสั้นแบบ kebab-case

COMMITfeat(payment): PAY-142 validate card

Conventional Commit + Jira key + สิ่งที่เปลี่ยน

PR TITLEPAY-142: Add card payment

เก็บ key ไว้ใน title แม้ใช้ squash merge

✓

กฎจำง่าย
หนึ่ง Jira ticket ควรสร้างหนึ่ง branch และหนึ่ง Pull Request ถ้า ticket ใหญ่จนต้องมีหลาย branch ให้แตกเป็น Jira subtasks ก่อน

2. ตั้งชื่อ branch ตามประเภทงาน

FEATUREfeature/PAY-142-card-payment

ความสามารถใหม่ตาม story

BUGFIXbugfix/PAY-203-gateway-timeout

แก้ defect ในงานปกติ

HOTFIXhotfix/OPS-77-restore-login

แก้ production เร่งด่วน

CHOREchore/DEV-91-upgrade-eslint

งานระบบหรือ maintenance

สร้าง branch จาก main ล่าสุด
$ git switch main
$ git pull --ff-only origin main
$ git switch -c feature/PAY-142-card-payment
